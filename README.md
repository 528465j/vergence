# Vergence
### Automated Data Quality and Reconciliation Pipeline

Two independent sources are supposed to describe the same figures. Often they
do not. This pipeline finds where they disagree, measures the
disagreement, explains where it came from, and never quietly resolves it.

The worked domain is financial: a General Ledger of individual transactions and
a Trial Balance summarising the same period. The pattern is general — any two
systems that should agree, arriving from providers who each name their columns
differently.

An LLM is used in exactly one stage, for exactly one task, behind a human
approval gate. Every figure the system reports is arithmetic.

## The name

Vergence is the measure of how far two lines are from meeting. Convergence and
divergence are the same word with the sign flipped, which is the point: a
difference between two sources is a quantity to be measured, not a fault to be
corrected. Where the vergence is zero the sources agree. Where it is not, that
is a finding, and the system's job is to size it and evidence it rather than
close it.

---

## The problem

Data arrives from many providers. Each one exports from a different system, so
the same field is called `Nominal Code` in one file, `GL_Acct` in another and
`Account_No` in a third. Amounts are inconsistent, rows are duplicated, dates
fall outside the period they claim to cover, and the summary does not always
agree with the detail it summarises.

The naive fix is a script per provider. That does not survive contact with
scale, because the number of scripts grows with the number of providers and
every one of them has to be maintained separately.

## What it does

| Stage | Module | Classification |
|---|---|---|
| 0 · Ingestion and registration | `src/s0_ingest.py` | Deterministic |
| 1 · Schema resolution and canonical mapping | `src/s1_mapping.py` | **LLM-assisted, human-gated** |
| 2 · Structural and type validation | `src/s2_validate.py` | Deterministic |
| 3 · Deduplication | `src/s3_dedupe.py` | Deterministic |
| 4 · Reconciliation controls | `src/s4_reconcile.py` | Deterministic |
| 7 · Reporting and audit trail | `src/s7_report.py` | Deterministic |

One codebase. Providers are added as configuration files, never as forks.

## Where a model is used, and where it is not

`src/s1_mapping.py` resolves incoming column names to the canonical schema in
three tiers: an exact match against a registry of previously approved mappings,
then deterministic synonym and fuzzy matching, and only then a model proposal
for whatever remains. Every proposal is constrained to the canonical field
enumeration by its type and carries a confidence score. Approving one writes it
to the registry, after which it resolves deterministically forever.

`resolve_columns` takes `llm=None` by default. **The model is never required to
reach a result.** Where the registry already carries a provider's columns it is
not called at all. On a new provider, disconnecting it leaves exactly the same
columns awaiting exactly the same decision — a person composes the mapping
rather than confirming a drafted one.

Every proposal is queued for review the first time a provider is mapped, and any
proposal below the confidence gate is queued whenever it appears. Once a person
has approved a provider, later proposals above the gate resolve without being
queued: approving one column is a decision about that provider as well as about
that column. That is a deliberate trade-off between control and throughput, and
it is the first thing to revisit if the tolerance for an unreviewed mapping is
lower than the tolerance for a stalled engagement.

Nowhere else in the system may a model speak. Balancing debits against
credits, agreeing a summary to its detail and detecting duplicates are
arithmetic, and arithmetic does not need a model.

### The dataset

Synthetic, and generated by `tools/make_synthetic_data.py`: a General Ledger
and a Trial Balance for one provider over one financial year, with five defects
planted in them deliberately so there is something for the controls to find. No
real data of any kind has ever passed through this system.

| Rows received | 59 |
| Rows accepted | 59 |
| Rows quarantined | 0 |

Nothing was quarantined because none of the planted defects is a structural
failure. A posting dated outside the period, a repeated line and a Trial
Balance that does not agree with its own movements are all valid rows. Each is
a finding for a control, and setting any of them aside would have removed the
evidence the control exists to report.

### Controls

Seven controls are registered and all seven ran. C5, the rollforward, reports
`SKIPPED — no prior period loaded`: there is one period of data, so there is no
prior closing balance to compare an opening balance against. It is implemented
and states why it could not run, rather than being absent and leaving a reader
to work out whether it was skipped or forgotten.

Nine exceptions were raised, seven above the configured materiality tolerance
and two below. Both are recorded; the tolerance decides whether a difference is
material, never whether it is reported.

### Five defects, nine exceptions

One root cause can fail more than one control, and each control reports its own
finding rather than the register collapsing them into a single line.

| defect | exceptions | controls |
|---|---:|---|
| D1 | 2 | C1, C2 |
| D2 | 3 | DEDUPE, C1, C2 |
| D3 | 2 | C2, C6 |
| D4 | 1 | C4 |
| D5 | 1 | C3 |

D2 is the one worth reading twice. A single General Ledger line is duplicated,
and three controls report it: DEDUPE finds the pair, the copy is a one-sided
debit so its journal no longer self-balances and C1 finds that, and the Trial
Balance was drawn up before the copy existed so the account no longer agrees
and C2 finds that. All three are valued at the same 1,200.00 — DEDUPE naming
both the journal and the account, C1 the journal, C2 the account. It is one
root cause reported three times, not three problems, which is why the
per-control values are stated separately and never summed.

Deleting the duplicate would have silenced all three. That is the reason stage
3 records a reversible decision and returns the population untouched: two
identical rows can be entirely legitimate, and removing one must never quietly
change what another control reports.

### First run against second

The two runs differ in how the columns were read. They do not differ in what
was found.

| | first run | second run |
|---|---:|---:|
| GL columns from the registry | 0 | 12 |
| GL columns from synonyms | 7 | 0 |
| GL columns from the model | 5 | 0 |
| Columns awaiting a decision, both files | 6 | 0 |
| Model calls | 2 | 0 |
| Exit code | 2 | 0 |

The registry ships empty, so the first run has six columns that neither the
registry nor the synonym list can settle. It stops before the controls and puts
them to a person, exiting 2. Approving them records nineteen columns across the
two files, and the second run resolves every one at tier 1 and asks the model
nothing.

The exception register does not depend on which tier resolved the columns.
Running the same two files a third way — with the provider known to the
registry but four of its General Ledger columns not, so the model resolves
those four and the run reaches the controls — produces a byte-identical
register, run identifier aside: the same nine findings, in the same order, at
the same values. Mapping decides how columns are read. It does not decide what
the controls find.

### Tests

Sixteen, all passing. Every control in the register has a test firing it on a
fixture built in the test to defeat it. C1 and C2 each have a second proving
they stay silent where they should, and C5 a second proving it reports
`SKIPPED` with its reason rather than simply finding nothing when no prior
period is supplied. Beyond those: that stage 3 returns
the population unchanged, that the control total holds on the real dataset and
raises on a broken row count, that the dataset quarantines nothing, that a full
run reproduces the planted defects manifest exactly — matched as a multiset, so
a repeated finding cannot collapse and hide a duplicate — and that `resolve_columns` completes with `llm=None`, which is what lets the deterministic tiers be exercised with no model present at all.

## Design decisions

- **Money is `decimal.Decimal`, never `float`.** Binary floating point
  manufactures sub-cent differences that look exactly like genuine breaks.
- **Validation quarantines; it does not coerce.** A row that fails its schema
  is set aside with its failing rule and its original values intact.
- **Nothing is deleted.** Every duplicate, proven or suspected, is flagged with
  a reversible decision record and the row stays in the population, so removing
  a row can never silently change what another control reports.
- **Differences are outputs, not failures.** The system is judged on how well
  it evidences a difference, not on whether it made one disappear.
- **Thresholds live in configuration.** Materiality belongs to the people who
  own the judgement, not to the code.

## Running it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python tools/make_synthetic_data.py

python -m src.run --client CLIENT_A          # first run stops for a decision
python -m src.approve --client CLIENT_A      # what needs deciding; writes nothing
python -m src.approve --client CLIENT_A --approve-all
python -m src.run --client CLIENT_A          # resolves from the registry, no model call

python -m pytest -q
```

The registry ships empty, so the first run of a provider has columns nothing
can resolve deterministically and stops rather than guessing. It exits 2 —
distinct from 0, a completed reconciliation, and from 1, a pipeline that could
not run — because work waiting on a person is not a failure.

## Scope and limitations

A scoped prototype against synthetic data, written to test whether the
architecture holds. Stages 5 (extracting fields from PDF source documents) and
6 (drafting narrative explanations of exception clusters) are designed but not
implemented. There is no user interface, no database and no deployment layer.
No real data of any kind has ever passed through it.

The model behind stage 1 is a deterministic stub. It proposes from a fixed
table rather than reasoning about a column, so a run is reproducible by anyone
who clones this repository and no key or network is needed to exercise the
path. The live client is written and left unwired; the seam it sits behind is
the point, not the model on the other side of it.
